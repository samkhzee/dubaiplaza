Complete proposed product & technical report · Web-only V1 + roadmap

Dubai Plaza Stock System

A cloud-first, multi-user browser web application for second-hand laptop dealers. V1 is deliberately a conventional website: no downloadable desktop application, no Android/iOS application, no PWA installation and no offline transaction mode.

1. Executive decision

The project should be built as a proper website/web application around the workflow search → inspect → sell → collect → understand profit. The strongest V1 choice is:

HTML5 + CSS3 + Bootstrap 5 + Vanilla JavaScript → Laravel + PHP → PostgreSQL

This is preferred over React + TypeScript + NestJS for V1 because it reduces architectural overhead while remaining fully capable of inventory, sales, customer credit, Excel import, reporting, authentication and future API access.

2. V1 scope

  • Secure login, owner/staff permissions and organization/shop isolation.
  • Serialized laptop inventory: one row per physical laptop.
  • Accessory inventory: chargers, RAM, SSDs, batteries and similar quantity stock.
  • XLSX/CSV import with preview, mapping, validation and lot/cost allocation.
  • Fast laptop search with normalized tokens and safe numeric matching.
  • Grouped search results with stock count and direct Sell action.
  • Sales with negotiated price, discounts, cash, partial payment and credit/Udhaar.
  • Customer ledger, payment history and outstanding balances.
  • Returns, warranty lookup and controlled corrections.
  • Historical profit using cost_at_sale.
  • Stock aging/dead-stock reporting, dashboard and audit logs.
  • Cloud database, automated backups and business-data export.
Not V1: Android/iOS app, downloadable desktop app, PWA, offline transactions/sync, barcode/QR hardware, voice search, AI assistant, full multi-branch operations, payroll, complex accounting and e-commerce integrations.

7. Why React + NestJS adds complexity

  • Separate frontend and backend application layers.
  • More state handling for forms, loading, caching, errors and mutations.
  • More dependency decisions for forms, validation, API data fetching and UI components.
  • Explicit API contracts between React and NestJS.
  • More decisions around authentication and token/session architecture.
  • More places for business logic to be incorrectly duplicated between client and server.
  • More deployment/monitoring components.

This is useful complexity when the product needs it. For V1 it is mostly overhead around relatively conventional inventory and business workflows.

9. Data-model rules

  • One laptop = one serialized unit record.
  • Accessories = quantity inventory.
  • Historical profit: copy cost_at_sale into each sale item.
  • Atomic selling: mark stock sold and create sale records inside one database transaction.
  • Tenant isolation: business-owned tables carry organization/shop boundaries.
  • Audit: price, stock, sale, return, payment and permission changes are traceable.

17. Security, Privacy & Confidential-Data Protection

Security is a core architectural requirement, not an optional feature. Dubai Plaza will handle customer contact information, payment/credit records, inventory costs, sales history and other commercially confidential information. V1 should therefore use a defense-in-depth security model with encrypted transport, controlled access, tenant isolation, protected secrets, encrypted backups, auditability and continuous testing.

Security principle: no client-side control, hidden button, URL pattern or JavaScript check is treated as an authorization boundary. Every sensitive action must be authenticated and authorized on the Laravel server before data is returned or changed.

17.2 Encryption model

Data location / stageProtectionRequirement
Browser → applicationHTTPS/TLSAll production traffic must use HTTPS. TLS 1.3 is preferred; TLS 1.2 may remain for compatibility where required.
Application → PostgreSQLDatabase TLSUse an encrypted PostgreSQL connection and verify the database certificate where supported.
Database at restManaged-storage/database encryptionProduction database storage must use provider-supported encryption at rest.
BackupsEncrypted backup storageBackups must be encrypted, access-controlled and separated from normal application credentials.
Uploaded XLSX/CSV/documentsPrivate object storage + encryption at restFiles must not be public by default. Use signed/authorized access when downloads are required.
Highly sensitive application fieldsApplication-level encryption where justifiedIdentify sensitive fields individually rather than encrypting everything, because encrypted fields may not support normal searching/indexing.
PasswordsOne-way password hashingPasswords must never be reversibly encrypted or stored in plaintext.
Encryption keys/secretsSecret/environment managementNever commit production secrets, database passwords or encryption keys to GitHub.
Important distinction: HTTPS/TLS protects information while it travels between browser and server. Encryption at rest protects stored information. True end-to-end encryption, where the server itself cannot decrypt the information, is a different model and would prevent normal server-side search, reporting and business processing unless a specialized E2EE architecture is introduced. For Dubai Plaza V1, use strong transport encryption + storage encryption + application controls rather than incorrectly claiming that normal HTTPS is “end-to-end encryption.”

17.3 Authentication

  • Use Laravel's established authentication mechanisms rather than building password handling from scratch.
  • Passwords must be securely hashed using a modern password-hashing algorithm supported by the framework.
  • Use secure, HttpOnly, SameSite cookies for browser sessions.
  • Enable session regeneration after authentication and prevent session fixation.
  • Use account lockout/rate limiting or progressive throttling for repeated failed logins.
  • Provide password reset using short-lived, single-use tokens.
  • Require MFA/2FA for the owner and other privileged accounts; strongly consider it for all users.
  • Provide secure logout and invalidate the session.
  • Automatic inactivity timeout should be configurable, with a shorter timeout for privileged operations if appropriate.

17.4 Access-control model

RoleTypical permissionsRestricted operations
OwnerAll shop data, users, settings, reports, financial information, audit logs, backups/export controls.None within the application; highly sensitive changes should require re-authentication/MFA.
ManagerInventory, sales, customers, payments, warranty, returns and approved reports.User administration, security settings and selected financial/audit operations.
StaffSearch inventory, inspect stock, create permitted sales, record permitted payments and view necessary customer information.Cost editing, permission changes, destructive administration and sensitive reports unless explicitly granted.
Server-side authorization rule: permissions must be enforced by Laravel policies/gates/service-layer checks on every protected request. A user must not gain access merely by changing an ID in a URL, modifying JavaScript, calling an endpoint directly or submitting a forged request.

17.5 Tenant and organization isolation

  • Every business-owned record must be linked to an organization/shop boundary.
  • Queries must scope records to the authenticated user's organization before returning data.
  • Never trust an organization ID supplied by the browser.
  • When V2 adds multiple branches, branch-level permissions must be enforced separately from organization-level permissions.
  • Automated tests must attempt cross-organization access and confirm it is denied.
  • Administrative jobs, exports and reports must apply the same tenant restrictions as normal pages.

17.7 Confidential customer-data policy

  • Collect only information necessary for sales, delivery, warranty, ledger and legitimate business operations.
  • Do not expose customer lists, phone numbers, addresses or balances to users who do not need them.
  • Do not place confidential customer information in browser URLs, analytics events or public logs.
  • Production logs must avoid passwords, authentication tokens, full payment credentials and unnecessary personal information.
  • Exports containing customer information must be permission-controlled and treated as confidential files.
  • Downloaded exports should not remain permanently exposed through public URLs.
  • Define retention/deletion rules appropriate to business and legal requirements before production launch.
  • When staff accounts leave the business, disable access immediately rather than sharing passwords.

17.8 Database and infrastructure security

  • PostgreSQL should not be directly exposed to the public internet in the normal production architecture.
  • Use a dedicated least-privilege database account for the application.
  • Separate production credentials from development/test credentials.
  • Restrict server/admin access using strong authentication and SSH keys or the cloud provider's secure access mechanisms.
  • Keep Laravel/PHP, PostgreSQL, operating-system packages and dependencies patched.
  • Use a firewall/security group to expose only required services.
  • Disable debug mode in production.
  • Use secure HTTP response headers such as Content-Security-Policy where compatible with the application, plus X-Content-Type-Options, Referrer-Policy and frame protections.
  • Centralize security monitoring/error tracking without sending unnecessary confidential customer information to third parties.

17.11 Security monitoring and audit

Record security-relevant events without logging unnecessary confidential content:

  • Successful and failed logins.
  • Password reset and MFA events.
  • User creation, role changes and account disabling.
  • Inventory cost/price changes.
  • Sales, refunds, returns and payment changes.
  • Customer ledger adjustments.
  • Exports and sensitive report access.
  • Authorization failures and suspicious repeated requests.

Audit records should be append-oriented and protected from ordinary staff modification. Administrative access to audit data should itself be controlled and logged.

17.14 Production security acceptance criteria

  • No production page or API accepts sensitive traffic over plain HTTP.
  • No production database port is publicly exposed unless explicitly justified and tightly restricted.
  • No user can access another organization's data by modifying URLs, request bodies or API parameters.
  • No staff user can promote their own role or alter their organization boundary.
  • No client-side JavaScript can override server-side price, cost, permission or stock rules.
  • Passwords, secrets and encryption keys do not appear in source control, frontend code or normal application logs.
  • Backups are encrypted and a restore has been successfully tested.
  • Critical security events are auditable.
  • Production debug mode is disabled and error responses do not reveal stack traces or secrets.
  • A security review is completed before real customer data is loaded.
Security target: the system should be designed so that confidentiality and integrity do not depend on users behaving honestly or on the browser behaving correctly. The server, database and infrastructure must independently enforce the security boundary.

16. Final recommendation

Use Option A for Dubai Plaza V1:

HTML5 + CSS3 + Bootstrap 5 + Vanilla JavaScript
+ Laravel + PHP
+ PostgreSQL
+ PhpSpreadsheet + Eloquent + Laravel Auth/Sanctum + Chart.js
+ Git/GitHub + Composer/npm + Postman

Do not choose React + NestJS merely because it is more modern. Choose it later if real usage proves that a highly component-driven frontend, larger SaaS scale, real-time interfaces or dedicated application clients justify the additional architecture.

Build the core correctly first. Optimize based on real usage. The first measurable outcome is not the number of technologies used; it is whether a shop employee can reliably search for the right laptop, inspect it, sell it, collect payment, record the customer's balance and see the correct profit.
